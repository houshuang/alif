# Review: Snap page pre-match (PR #363), 26 November 2026

Read-only review of `backend/app/services/snap_prematch.py` and its callers, against the
production export (16 pages, 2,183 stored surfaces) and the 113 glosses the pass wrote.
Lemma facts were checked against the pre-pass database copy in the scratchpad.

Contents: 1. the 113 written widenings; 2. output quality on the pages; 3. logic review;
4. ranked fix list.

---

### 1c. No-value rewrites (10)

#21 مقاطعة, #34 أسماء, #49 ولاية, #64 عديد (reorderings); #82 أخفى (`to hide, to conceal` → `to hide, conceal`), #83 مبيع, #99 بدا (punctuation or order only); #79 عودة, #101 طب, #107 ميل (a synonym). Each cleared the lemma's memory hook.

### 1d. Patterns behind the bad ones

1. **"broader" used where the right verdict was "different"** (حياته, بعكس). `_is_widening` passes because one old word survives in the new gloss.
2. **The prompt orders "the meaning used here first"**, so every page reorders a gloss around its own sense. The same lemma was rewritten twice in one day three times (نَفْس, عَدِيد, ضَمان).
3. **Stored meanings are not actually kept.** `_is_widening` requires one shared word of three or more letters. Meanings were dropped in #43, #46, #63, #66, #94, #106.
4. **Idioms and names of this book** enter the general gloss (7 cases).
5. **Not sentence-driven additions** (سَمَّى "to poison", جَعَلَ "to begin to", أَمْضَى "to carry out"): the model rewrites a gloss it finds thin. Two were correct, one was wrong.

## 3. Logic review

### Real defects

**D1. Background widenings are written without anyone seeing them, and 12 % are bad.**
Before, a widening happened only on a tapped word and the card said "Gloss widened (was: …)". Now about seven glosses per page change for words nobody tapped, 74 % of them on `known` words. Failure scenario (happened): page 15 → حَيّ becomes "life; alive"; every later card and lookup of حَيّ teaches it. There is no per-write log (`snap_prematch` logs counts only; pre-read logs `preread_regloss`, the per-tap path logs `gloss_from`/`gloss_to`). The only record is `prematch_json`, which the next pass over that page overwrites.

**D2. `_is_widening` does not enforce "keeps the stored meanings".**
One shared word passes. It lets through a different word's meaning (حياته), dropped meanings (مَطَاف), and a narrowing (عَشْرَة). Combined with "meaning used here first" and repeated passes, a gloss is reordered page after page and old meanings fall off at the 90-character cap.

**D3. An omitted line is stored as `fits`.**
`v = verdicts.get(i) or {"verdict": "fits"}`. The per-tap check returned an explicit verdict per word. Evidence: the page 11/12 rerun (4 of 12 other-word cases lost), أعصاب → "to twist" on page 15, كمال → "money" on page 7. A tap then shows the wrong entry instantly with no "checking" state and never reaches the live check.

**D4. No `name` verdict in the batched check.**
The prompt says not to report "words used as part of a name". Result: names either stay `fits` on a common word (جلال "to be great", جيليه "generation", جان "guilty") or come back as `different` → new noun with `is_proper_noun: False` and an Add button. The per-tap path showed these as names.

**D5. One stored answer per surface per page.** See الحديث above. The live path keyed on token + sentence.

**D6. Every widening clears the memory hook, and nothing regenerates it here.**
`regloss()` returns the ids whose hooks it cleared; pre-read passes them to `_prepare_material`, `snap_prematch` discards them. 80 of 110 lemmas lost their hook, ten of them for a reorder or a comma. Hooks come back lazily after a failed review, so this is a loss of existing content, not a permanent gap.

**D7. A pass with failed chunks is stored as `ready` and never retried.**
`needs_pass()` retries only `status == "failed"`. If the Claude CLI is unavailable (the weekly limit was hit on 25 November), `check_senses` returns `None` for every chunk, the page is stored `ready` with `failed_checks` = all and few words, and taps on that page use the slow path permanently. `unmatched_ok = False` is likewise logged but not stored.

**D8. Finished pass can be started a second time.**
`get_snap_prematch` reads the page first and checks `is_running` afterwards. If the pass stores and leaves `_running` between those two steps, the request sees the old empty `prematch_json` with `is_running == False` and schedules a full second pass (four model calls, and a second round of widening on the glosses the first pass just wrote). The window is milliseconds, the poll is every 3 s. Fix: check `is_running` before loading the page, or reload the page after the check.

**D9. The second `broader` verdict for one lemma on a page is shown but not stored.**
The compare-and-set uses the gloss from the start of the pass, so after the first write the second fails (`written: False`). The card still shows the second proposal as the gloss (`snap.tsx` line 751), without the "Gloss widened" note. Five cases, e.g. page 7 نفوسه, page 14 للضمان "security (social security); …" while the database has another text.

### Smaller points

- **Stale answers.** The endpoint refreshes `knowledge_state` only. Stored `gloss_en`, `lemma_ar` and `lemma_id` stay as they were at pass time: a repaired gloss does not reach old pages, a merged or deleted lemma id stays in the page, and a `different` → new proposal that the learner has since added still has `lemma_id: null` after a reload (the live path would find the new entry through `_resolve_different_word`).
- **Fallback models write glosses.** `check_senses` asks for `claude_sonnet`; when the CLI fails the chain goes to the API models, and their verdicts are written the same way. Nothing records which model produced a written gloss (CLAUDE.md rule 13).
- **Write-lock discipline (rule 10): no violation found.** The model calls run with no dirty session. `_unmatched_words` keeps a read transaction open during the gloss call (about 20 s), which blocks nothing but a WAL checkpoint. Writes in the result loop are single-row with a commit each.
- **`/snap` checks its chips with the same batched call and then the pass checks those words again**; the compare-and-set makes this safe, it is only a repeated call.
- **Frontend keying.** `ARABIC_TOKEN` in `snap.tsx` is character-for-character the backend `_ARABIC_TOKEN`; all 2,183 stored keys are tokens of their page text. A whitespace token with two Arabic runs ("جان-ميشال" without spaces) falls back to the live path, which is correct. Tokens from the aligned-sentence view (`asToken`) use the OCR sentence text; where that differs from `arabic_text` the key misses and the live path runs.
- **Vocalization-variant duplicates.** `validate`'s "same citation form" guard compares `_vocalized_key`, so فُؤاد vs فُؤَاد or ثَّانِي vs ثَانٍ count as different words and the existing entry is offered as new. Shared with the per-tap path.
- **Tests.** No test covers two surfaces of one lemma both `broader`, the `sibling` branch, a pass with failed chunks followed by `needs_pass`, or a name.

### Checked and not a problem

- Homograph grouping in `discover_words_in_text` (two tokens that resolve to different entries with the same bare key are grouped under the first). Measured on the database copy for pages 1–4: 523 surfaces, the page pass and a single-token lookup gave the same entry for all 523. Three surfaces differed only in the same-spelling candidates offered: the page pools the ties of all grouped surfaces, so المنطقة / منطقة get candidate 3891 and the vocalized تأثَّر (which the resolver decided on its own) gets candidate 5588 from another surface. That widens the room for a wrong `sibling` answer slightly; minor.
- `run_prematch` single-flight, restart during a pass (the next GET starts a new one), `_store` ordering before `_running.discard`.
- Compare-and-set against concurrent edits.

## 4. What to fix, ranked

1. **Revert or rewrite the 14 bad glosses** (table 1a), and look at the 11 doubtful ones. Most urgent: حَيّ, عَكَسَ, سَمَّى, عَشْرَة, سيّء, نَفْس.
2. **Stop writing widenings in the background.** Keep the proposal in `prematch_json` as display text for that page, and write only when the learner taps the word (as before), or queue it for review like add-checks. At minimum log every write (`lemma_id`, from, to, page, model).
3. **Tighten `_is_widening`**: require every stored meaning segment to survive, refuse a new first segment that is an idiom or name, refuse when the surface's part of speech differs from the entry's, and stop asking for "the meaning used here first" on stored glosses.
4. **Make the batched check return a verdict for every line** (including `fits` and `name`), and treat a missing line as unchecked so the tap uses the live path.
5. **Carry `name` through**: set `is_proper_noun` on name results and do not offer Add.
6. **Do not clear memory hooks for reorders or punctuation**, and regenerate cleared ones as pre-read does.
7. **Retry partial failures**: `needs_pass` should rerun when `failed_checks` is a large share or `unmatched_ok` is false.
8. **Per-occurrence answers** for surfaces that occur more than once on a page (or fall back to the live check for those 8 %).
9. Smaller: the double-start window (D8), the `written: False` display (D9), refreshing glosses and ids in the endpoint.
